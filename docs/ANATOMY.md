# Component anatomy

What every Atoll component is made of, which parts you can change and which you can't. Each component's own docs page then shows its specific anatomy: a **Component Structure** snippet (the parts and how they nest), a **Properties** table per part (generated from the source), and, where it has one, the **Keyboard and accessibility** contract.

## The three layers

```text
┌───────────────────────────────────────────────┐
│ Your app: layout, content, state, your class  │  yours: change anything
├───────────────────────────────────────────────┤
│ Styled layer (crates/ui/src/components/<name>)│  customizable: tokens, variants,
│   component.rs: props, variants, parts        │  class/style/attributes, slots,
│   style.css:   looks, in theme tokens only    │  strings
├───────────────────────────────────────────────┤
│ Primitive (atoll-primitives, our fork of      │  fixed: markup, roles, ARIA,
│ dioxus-primitives) or native HTML elements    │  focus and keyboard behaviour
└───────────────────────────────────────────────┘
```

1. **Primitive.** Behaviour and accessibility: the element structure, roles, `aria-*` wiring, focus management and keyboard handling. Interactive components (dialog, menu, select, tabs, slider, ...) sit on a `dioxus-primitives` component; simple ones (badge, card, alert) on plain HTML elements. This layer is fixed: restyling never changes its markup ([GUARDRAILS.md](GUARDRAILS.md)), because the ARIA and keyboard behaviour depend on it. A bug here is fixed in the primitive fork, with a test.
2. **Styled layer.** The kit's component: the props you pass, the variant enums, the parts, and `style.css`. Its class names are generated by `#[css_module]` (hashed), so you style it through the hooks below, not by targeting its classes.
3. **Your app.** Everything around and inside the component: layout, content in `children` and slots, state, and your own classes.

## The files of a component

| File | What it holds | Generated? |
|---|---|---|
| `component.rs` | The public components (`#[component] pub fn`), their props and variant enums | no |
| `style.css` | Looks, using theme tokens only (`var(--...)`) | no |
| `docs.md` | Description, Component Structure, accessibility notes, stability | no |
| `contract.toml` | Keyboard and accessibility contract: ARIA pattern, parts, states, keys; each key row is a test ([CONTRACTS.md](CONTRACTS.md)) | no (28 of 80 components have one) |
| `component.json` | What `dx components add` and `atoll add` copy, and the dependencies | yes, by `atoll registry` |
| `crates/ui/src/demos/<name>.rs` | The demo the gallery, docs site and tests render | no |
| `crates/ui/tests/components/<name>.rs` | The component's own tests | no |

## What you can customize

| Hook | How | Example |
|---|---|---|
| Theme tokens | Override CSS variables globally, per subtree (`data-theme` on any element) or per accent | `--radius: 0.25rem;`, `data-accent="violet"` |
| Variants and sizes | The component's enums (`#[non_exhaustive]`, so new ones aren't breaking) | `Button { variant: ButtonVariant::Ghost, size: ButtonSize::Sm }` |
| `class`, `style` and HTML attributes | Most parts take `attributes` that extend an HTML element; `class` is merged with the component's own | `Card { class: "settings-card", style: "max-width: 28rem" }` |
| Children and slots | `children` for the main content; some parts take named `Element` slots (`toolbar`, `footer`, `actions`, `avatar`, `icon`) or render callbacks (`render_cell`) | [COMPOSITION.md](COMPOSITION.md) |
| Data attributes | Style states with the attributes the kit and primitives render (`data-state`, `data-disabled`, `data-invalid`, `data-size`, `data-variant`, `data-slot`, ...) | `.settings-card [data-slot="card-header"] { ... }` in your CSS |
| Strings | Every visible kit string ("Close", "Next page", month names) comes from `UiStrings` | `UiStringsProvider { strings, ... }` ([RTL.md](RTL.md)) |
| The source itself | `atoll add` copies the component into your app; from then on it's your code, and `atoll update` merges upstream changes three ways | `atoll add dialog` |

## What you can't (and why)

- **Change a primitive's element structure or ARIA** from the styled layer or your app: it breaks keyboard and screen-reader behaviour that the tests prove. If you need different behaviour, open a feature request; if you copied the component, you can, but the kit's tests no longer cover your copy.
- **Rely on generated class names**: they are hashed and change. Use `class` and data attributes.
- **Remove an accessible name**: required names (`Dialog::title`, `IconButton::label`, chart `label`) are required props. Hide them visually (`hide_title`) instead of leaving them out.
- **Add layout inside a part with global CSS**: parts have their own layout (gaps, alignment, overflow). Put your layout in a wrapper or in `style`, so a kit update can't break it.

## Layout limits worth knowing

- Floating content (tooltip, popover, hover card, menus, select, combobox) flips at screen edges with CSS anchor positioning where the browser has it; older engines keep a fixed side ([SUPPORT_MATRIX.md](SUPPORT_MATRIX.md)).
- Overlays (dialog, sheet, drawer, alert dialog) cover the window with `position: fixed` and trap focus while open. An ancestor with `transform` or `filter` makes `fixed` relative to that ancestor in CSS, so keep overlays out of transformed containers.
- Charts size to their container's width and a `height` prop; give the container a width.
- `Textarea` grows with its content where the browser has `field-sizing: content`; elsewhere it keeps a fixed height.

## Which docs pages show a Component Structure

44 of the 80 components have a **Component Structure** section in their `docs.md`. Every component's page has the generated **Properties** tables, which list each part. The 36 still without a structure snippet are listed in `crates/cli/tests/maintenance.rs`; that test fails when a new component ships without one, and when a listed one gains a section without being taken off the list, so the gap only shrinks.
